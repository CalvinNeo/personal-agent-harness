# 自定义修改清单

这个仓库整理了围绕 AstrBot 4.29.3 的自定义代码、系统服务模板和运维工具。它是经过脱敏、参数化的参考版本，不是服务器目录的完整备份。线上已有的授权群、用户、模型提供商地址、凭据和运行数据需要在部署机器上另行配置。

| 范围 | 代码位置 | 修改后的行为 |
| --- | --- | --- |
| 本地提醒 | `plugins/reminder/` | 支持命令和明确的自然语言提醒，持久化单次任务，在到期时发送真正的 QQ `@` 提醒。 |
| 图片上下文 | `plugins/image_context/` | 暂存同一发送者最近的图片，使后续“刚发的那几张图”能够引用对应图片。 |
| Codex 接入 | `plugins/codex_bridge/` | 通过命令、自然语言和受限语义工具提交复杂任务，使用状态看板和原始 QQ 回执回传异步结果。 |
| Codex 会话续接 | `services/conversations.py` | 保存真实原生 session ID、按 owner 隔离原图和工作区；引用 Codex 回复时续接原会话。 |
| 轻量意图路由 | `plugins/intent_router/` | `regex` 使用现有规则；`light` 用独立 GPT-6 Astra low 做固定枚举路由，失败自动回退。 |
| Codex 执行进程 | `services/codex-runner.py`、`services/media.py` | 以独立低权限账户执行任务，校验 Unix socket 对端身份，限制工作目录、执行时间、图片和输出大小。 |
| 模型代理 | `services/codex-api-proxy.py` | 在本机代理模型请求，将上游模型密钥与 Codex 任务进程分开保存。 |
| AstrBot 内置功能修正 | `patches/`、`scripts/apply_patches.py` | 修正 AnySearch 区域参数，并移除模型限流重试日志中的密钥前缀。 |
| 部署与访问限制 | `deploy/`、`scripts/` | 提供专用账户的 systemd 服务、本机端口限制、默认拒绝的配置初始化及检查工具。 |

## 提醒：识别、调度与真实 @

提醒由本地解析器和调度器处理，不需要调用 Codex，也不需要模型来解释标准时间表达式。可以在授权群中 @机器人后发送：

- `两分钟后提醒我喝水`
- `请在半小时后提醒我开会`
- `提醒我明天下午三点开会`
- `/提醒 2分钟后喝水`
- `/提醒列表`
- `/提醒取消 <ID>`

解析器支持中文数字、半分钟等时长以及日期、时刻表达式，按 `Asia/Shanghai` 解释本地时间。只有明确的提醒请求才会创建任务；含糊时间、缺少内容以及暂不支持的请求会要求补充或说明限制。自然语言入口要求明确 @机器人或使用既有唤醒方式，避免普通聊天触发。转发、引用内容不会直接当作新提醒指令执行。

任务以原子写入方式保存为私有 JSON 文件，记录创建者、会话、时间和内容。重启后会重新读取待办任务。默认延迟范围为 5 秒至 7 天，默认每群最多 20 条、每人最多 10 条，每条内容最多 500 字；这是单次提醒，不是重复日程系统。

QQ 官方适配器在纯文本消息中会直接显示 `<qqbot-at-user ... />`。提醒消息单独启用 Markdown，并使用 AstrBot 的 `At` 消息组件，使 QQ 解析成真正的 @。这不要求把所有机器人回复都改成 Markdown。

发送时先尝试群消息接口，必要时使用仍在内存中的原始 QQ 事件回复。失败后间隔 30 秒重试，最多尝试 5 次；达到上限后移除任务。平台不可用返回 `False` 时会视为失败，不会误标为已发送。它不是“保证送达”队列，QQ 权限、回复时限、限流和网络故障仍可能影响结果。

## 图片：按发送者保存最近上传的引用

图片缓存按“完整会话 UMO + 发送者”隔离，默认有效期 30 分钟，每人每群最多 12 张，总共最多 64 个发送者会话。相邻上传间隔不超过 2 分钟的图片视为同一批：

- “上一张图”选择最近一张。
- “刚才三张图”选择最近三张。
- “刚发的那几张图”选择最近一批。

只记录 QQ 官方平台实际推送的顶层图片，不递归读取引用或转发图片。QQ 如果不推送未 @机器人的图片消息，发送图片时也必须 @机器人。图片不存在或数量不足时会提示重新发送。

缓存仅保留受支持 QQ 图片域名的 HTTPS URL，不由插件下载图片或写入文件，重启后清空。在后续图片引用请求中，插件去掉上下文中的历史图片，注入当前发送者选中的图片，降低混用他人图片的风险。注入使用临时消息组件，不额外加入持久化聊天记录；AstrBot 为调用模型所进行的临时文件处理仍由框架管理。

这项功能通过普通图片模型完成，不经过 Codex。提供商需要实际支持图片输入。缓存隔离也不代表群文字历史隔离：AstrBot 原有群会话中的文字上下文是否共享，仍由会话配置决定。

## Codex：显式执行与异步回传

`/codex <任务>` 和 `/cx <任务>` 才会进入独立执行器。默认只读；`/codex write <任务>` 还需要发送者位于单独的 `write_senders` 白名单中。普通聊天、提醒和图片引用不会自动升级成 Codex 任务。

执行器使用 Linux Unix socket，校验连接进程的 UID。每个群会话对应一个由会话标识哈希生成的工作目录；同群授权用户会共享这个工作区，并非每个用户一个目录。任务使用 Codex 的只读或工作区写入沙箱，以独立服务账户运行，同时限制任务并发、时限、输入和输出大小。systemd 进一步限制可写目录、权限与资源。

异步回传保留原始 QQ 事件，让适配器能使用原消息标识回复，修复直接用主动消息接口回传时被平台拒绝的问题。原始消息的有效期和平台配额仍然适用，长任务或进程重启后不保证可回传。

上游密钥保存在独立代理账户可读的私有文件中，由本机代理附加到模型请求。Codex 任务环境不直接携带该上游密钥。输出还会做有限的密钥模式脱敏，但不能把它当作通用敏感信息检测器。

这些措施不构成完整的出站网络隔离。模型请求必然发送到配置的提供商；主机 root、服务配置和依赖供应链仍属于信任边界。升级 Codex、AstrBot 或 Linux 沙箱相关组件时，需要重新检查限制是否生效。

## 两处 AstrBot 源码补丁

以原始 AstrBot 4.29.3 wheel 为基线，对已部署的 AstrBot Python 文件逐一比对后，发现两处差异：

1. `astrbot/core/provider/sources/openai_source.py`：模型请求限流重试时，用固定脱敏文本代替 API key 前缀日志。
2. `astrbot/core/tools/web_search_tools.py`：把 AnySearch 的 `global` 区域选项映射为接口接受的 `intl`。

网页搜索本身使用 AstrBot 内置工具，启用配置及通用示例一并保留。搜索请求会联系所配置的搜索服务，结果随后进入模型上下文。

安装的 `qq-botpy==1.2.1` 中带分发校验值的 Python 文件与原始校验值一致，未发现该 SDK 的 Python 源码修改。仓库不重复收录整个 AstrBot 或 QQ SDK，也不把它们描述为自研功能。补丁仅适用于固定版本；升级时应重新比较和移植，不能盲目覆盖新版本文件。

## 默认关闭与未纳入内容

自定义插件均以 `allowed_umos` 精确匹配允许的会话，空列表拒绝所有会话。`allowed_senders` 是进一步限制：在已允许的会话内，空列表表示不再限制发送者；Codex 的 `write_senders` 空列表则表示没有人能使用写入模式。框架层的会话白名单与插件白名单都要配置，不能只修改其中一个。

管理后台和模型代理只监听回环地址，通过 SSH 隧道管理；Codex 执行器只暴露本机 Unix socket。部署模板使用专用服务账户、严格文件权限和有限资源，避免把执行器当作 root 运行。

以下内容不属于仓库资产：真实服务器地址、QQ 应用凭据、群和用户标识、模型密钥及私人提供商地址、管理后台密码、聊天数据库、提醒记录、日志、图片 URL、Codex 工作区和会话历史、SSH 密钥以及线上配置文件。仓库中的占位符和默认拒绝配置需要在目标机器上补全，不能直接复制线上私有目录来“补齐”。
